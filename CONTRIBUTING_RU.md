# Участие в проекте

[English](CONTRIBUTING.md) · [**Русский**](CONTRIBUTING_RU.md)

Спасибо, что заинтересовались Noetec! Нам пригодится помощь любого масштаба: подробный
отчёт об ошибке ценен ничуть не меньше, чем тщательно доведённая фича. Если что-то
работает не так, как должно, проще всего помочь, открыв issue, — для этого не нужно
писать ни строчки кода.

Участвуя в проекте, вы обязуетесь соблюдать наш
[Кодекс поведения](CODE_OF_CONDUCT_RU.md). О неприемлемом поведении сообщайте
по указанному в нём контакту.

## Как ведётся разработка

Noetec — личный проект, и часть повседневной работы в нём выполняют ИИ-агенты,
которые опираются на документацию в репозитории. Для вас это ничего не меняет:
вклад людей проходит ровно такое же ревью. Любой PR, кем бы он ни был написан —
человеком или агентом, — одинаково проверяется на GitHub, прежде чем его можно будет влить.

## Как сообщить об ошибке

Откройте issue на GitHub по
[шаблону отчёта об ошибке](https://github.com/LonelyGriffin/noetec/issues/new?template=bug_report.yml).
В шаблоне нужно указать:

- **Шаги воспроизведения** — минимальную последовательность действий, которая вызывает ошибку.
- **Ожидаемое и фактическое поведение.**
- **Окружение** — ОС, версию приложения и версии Flutter/Dart SDK.

Чем точнее описание, тем проще исправить ошибку. Если она касается безопасности
(приложение работает с криптографией и синхронизацией), **не** открывайте публичный
issue, а действуйте по инструкции из [SECURITY_RU.md](SECURITY_RU.md).

## Как внести изменение

### 1. Начните с issue

Прежде чем писать код, откройте issue с описанием проблемы или новой возможности
(по шаблону отчёта об ошибке или запроса фичи). Так мы убедимся, что движемся
в верном направлении и не делаем одну и ту же работу дважды. Если issue уже
есть, переходите сразу к шагу 2.

### 2. Форк и ветка

1. Сделайте форк репозитория в свой аккаунт GitHub (участники с правом записи
   могут создавать ветки прямо от `main`).
2. Создайте ветку под issue. В репозитории принято заводить по одной ветке на issue
   и называть её по ключу issue (например, `NOET-42`).

### 3. Разберитесь в кодовой базе

Перед тем как что-то менять, прочитайте [`docs/architecture.md`](docs/architecture.md) (на английском) —
обзорную карту того, что где находится (системы, DI, цикл потока данных),
со ссылками на ADR и спецификации, где объясняется «почему» и описан сам контракт.

### 4. Внесите изменение

- Обоснование каждого крупного решения описано в
  [docs/decisions/](docs/decisions/) (ADR неизменяемы: чтобы изменить решение,
  пишут новый ADR, а не правят старый).
- Для нового поведения добавляйте модульные и виджет-тесты в `test/`,
  повторяя структуру `lib/`.
- Никогда не правьте сгенерированные файлы (`*.g.dart`, `*.freezed.dart`) —
  вместо этого перегенерируйте их командой `dart run build_runner build`.
- Никаких `print()` в продакшен-коде — используйте `package:logging`.

### 5. Откройте PR

Запушьте ветку и откройте пул-реквест в `main`, заполнив шаблон PR (что
изменилось, зачем и как это проверялось).

### 6. Ревью и слияние

- Архитектор проекта проверяет PR с точки зрения архитектуры и выбранного подхода;
  вы получите комментарии к строкам кода и итоговый вердикт в PR.
- Исправления по замечаниям пушьте в ту же ветку — новый PR открывать не нужно.
- Вливать изменения в `main` может только владелец проекта, и защита ветки это
  гарантирует: автор никогда не вливает свой PR сам, даже самый маленький.

## Релизы

Выпуск версий Noetec описан в
[`docs/release-process.md`](docs/release-process.md) (на английском): changelog
(`CHANGELOG.md`, формат Keep a Changelog) обновляется в каждом PR с заметными
для пользователя изменениями, а релиз — это повышение версии, тег и GitHub Release,
собранный по changelog.

## Переводы

Английский текст канонический. Русский перевод есть только у файлов для
сообщества — README, CONTRIBUTING, SECURITY, SUPPORT и CODE_OF_CONDUCT — в виде
`<name>_RU.md` рядом с оригиналом. Вся остальная документация (`docs/`, CHANGELOG,
ROADMAP, CLAUDE) ведётся только на английском; новые переводы не добавляются.

- Если меняется файл из пары, `_RU`-версия обновляется в том же PR.
- В шапке пары стоит переключатель `[**English**](X.md) · [Русский](X_RU.md)`,
  текущий язык выделен жирным.
- Ссылки из `_RU`-файла на документ без перевода ведут на английский оригинал.

## Настройка окружения

Понадобится свежий Flutter SDK (Dart 3.10 или новее).

```bash
git clone https://github.com/LonelyGriffin/noetec.git   # или ваш форк
cd noetec
flutter pub get
dart run build_runner build
dart run scripts/setup_project.dart   # устанавливает git-хук pre-commit
```

Хук pre-commit форматирует код, запускает статический анализ и проверяет заголовки
с копирайтом в проиндексированных файлах, так что большинство проблем всплывает
ещё до коммита.

### Повседневные команды

Все команды запускаются из корня репозитория.

| Команда | Назначение |
|---|---|
| `dart run scripts/format.dart` | Форматирование проекта (ширина строки 180 и висячие запятые, настройки из `formatter:` в `analysis_options.yaml`) |
| `dart run scripts/lint.dart` | Полный линт: проверка форматирования, `dart analyze` и заголовков с копирайтом |
| `flutter test` | Запуск модульных и виджет-тестов (`test/`) |
| `dart run build_runner build` | Кодогенерация (json_serializable и т. п.) — запускайте после изменения сериализуемых классов |
