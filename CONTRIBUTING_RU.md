# Участие в проекте

[English](CONTRIBUTING.md) · [**Русский**](CONTRIBUTING_RU.md)

Спасибо, что заглянули в Noetec! Мы рады вкладу любого размера — хорошо описанный
отчёт об ошибке не менее ценен, чем отполированная функциональность. Если что-то
работает не так, как ожидалось, быстрее всего помочь — открыть issue, даже если вы
не напишете ни строчки кода.

Участвуя в проекте, вы соглашаетесь соблюдать наш
[Кодекс поведения](CODE_OF_CONDUCT_RU.md). Пожалуйста, сообщайте о неприемлемом
поведении по контакту, указанному там.

## Как устроена работа над проектом

Noetec — личный проект, и часть повседневной разработки выполняют ИИ-агенты,
работающие по документации в репозитории. Для вас это ничего не меняет: вклад
людей проходит точно такое же ревью. Каждый PR — написанный человеком или
агентом — проверяется на GitHub одинаково, прежде чем его можно будет влить.

## Сообщить об ошибке

Откройте issue на GitHub по
[шаблону отчёта об ошибке](https://github.com/LonelyGriffin/noetec/issues/new?template=bug_report.yml).
Шаблон просит:

- **Шаги воспроизведения** — кратчайшая последовательность, приводящая к ошибке.
- **Ожидаемое и фактическое поведение.**
- **Окружение** — ОС, версия приложения и версии Flutter/Dart SDK.

Чем конкретнее отчёт, тем проще исправить. Если ошибка связана с безопасностью
(приложение работает с криптографией и синхронизацией), **не** открывайте публичный
issue — следуйте [SECURITY_RU.md](SECURITY_RU.md).

## Как внести изменение

### 1. Сначала откройте issue

Прежде чем писать код, откройте issue с описанием проблемы или функциональности
(используйте шаблон отчёта об ошибке или запроса функциональности). Это
гарантирует, что направление верное, а работа не дублируется. Если issue уже
существует, сразу переходите к шагу 2.

### 2. Форк и ветка

1. Сделайте форк репозитория в свой аккаунт GitHub (участники с правом записи
   могут ветвиться напрямую от `main`).
2. Создайте ветку под issue. В репозитории принято по одной ветке на issue,
   названной по ключу issue (например, `NOET-42`).

### 3. Разберитесь в кодовой базе

Перед изменениями прочитайте [`docs/architecture_RU.md`](docs/architecture_RU.md) —
карту верхнего уровня, где живёт каждая тема (системы, DI, цикл потока данных),
со ссылками на ADR и спецификации, которые задают «почему» и сам контракт.

### 4. Внесите изменение

- «Почему» каждого крупного решения живёт в
  [docs/decisions/](docs/decisions/) (неизменяемые ADR — изменение ADR оформляется
  новым ADR, а не правкой старого).
- Добавляйте модульные и виджет-тесты, повторяющие структуру `lib/`, в `test/` —
  под новое поведение.
- Никогда не правьте сгенерированные файлы (`*.g.dart`, `*.freezed.dart`) —
  перегенерируйте их через `dart run build_runner build`.
- Никаких `print()` в продакшен-коде — используйте `package:logging`.

### 5. Откройте PR

Запушьте ветку и откройте пул-реквест в `main`, заполнив шаблон PR (что
изменилось, почему и как проверялось).

### 6. Ревью и слияние

- Архитектор проекта проверяет PR на соответствие архитектуре и подходу; вы
  получите комментарии по строкам и вердикт в PR.
- Учтите замечания, запушив изменения в ту же ветку — не открывайте новый PR.
- В `main` вливает только владелец проекта; защита ветки это обеспечивает, поэтому
  PR никогда не вливается автором, каким бы маленьким он ни был.

## Релизы

Версии Noetec следуют процессу в
[`docs/release-process_RU.md`](docs/release-process_RU.md): changelog
(`CHANGELOG_RU.md`, формат Keep a Changelog) обновляется в каждом PR,
заметном для пользователя, а релиз — это повышение версии + тег + GitHub Release,
собранный из changelog.

## Настройка окружения разработки

Требуется свежий Flutter SDK (Dart 3.10 или новее).

```bash
git clone https://github.com/LonelyGriffin/noetec.git   # или ваш форк
cd noetec
flutter pub get
dart run build_runner build
dart run scripts/setup_project.dart   # устанавливает git-хук pre-commit
```

Хук pre-commit выполняет форматирование, ограниченный статический анализ и проверку
заголовков копирайта на проиндексированных файлах, поэтому большинство проблем
ловится ещё до коммита.

### Повседневные команды

Все команды выполняются из корня репозитория.

| Команда | Назначение |
|---|---|
| `dart run scripts/format.dart` | Форматирование проекта (ширина строки 180 + висячие запятые, из `formatter:` в `analysis_options.yaml`) |
| `dart run scripts/lint.dart` | Полный линт: проверка формата + `dart analyze` + заголовки копирайта |
| `flutter test` | Запуск набора модульных и виджет-тестов (`test/`) |
| `dart run build_runner build` | Генерация кода (json_serializable и т. п.) — запускать после изменения сериализуемых классов |
