# Участие в проекте

[English](CONTRIBUTING.md) · [**Русский**](CONTRIBUTING_RU.md)

Спасибо, что заинтересовались Noetec! Нам пригодится помощь любого масштаба: подробный
отчёт об ошибке ценен ничуть не меньше, чем хорошо подготовленное изменение. Если что-то
работает не так, как должно, проще всего помочь, открыв issue, — для этого не нужно
писать ни строчки кода.

Участвуя в проекте, вы обязуетесь соблюдать наш
[Кодекс поведения](CODE_OF_CONDUCT_RU.md). О неприемлемом поведении сообщайте
по указанному в нём контакту.

## Как ведётся разработка

Noetec — личный проект, который разрабатывается в том числе с помощью ИИ-агентов. Все изменения
проходят проверку перед слиянием; окончательное решение принимает владелец репозитория.

## Как сообщить об ошибке

Откройте issue на GitHub по
[шаблону отчёта об ошибке](https://github.com/LonelyGriffin/noetec/issues/new?template=bug_report.yml).
В шаблоне нужно указать:

- **Шаги воспроизведения** — минимальную последовательность действий, которая вызывает ошибку.
- **Ожидаемое и фактическое поведение.**
- **Окружение** — ОС и версию приложения или коммит, если они известны.
  При запуске из исходников укажите версии Flutter/Dart SDK.

Чем точнее описание, тем проще исправить ошибку. Если она касается безопасности
(приложение работает с криптографией и синхронизацией), **не** открывайте публичный
issue, а действуйте по инструкции из [SECURITY_RU.md](SECURITY_RU.md).

## Как внести изменение

### 1. Обсудите изменение

Перед началом работы проверьте существующие issue. Если подходящее уже есть,
прочитайте обсуждение и оставьте комментарий о том, что хотите взяться за задачу;
проверьте, не работает ли над ней кто-то другой.

Для существенных изменений при необходимости откройте issue по шаблону отчёта
об ошибке или запроса новой возможности и согласуйте подход с владельцем репозитория
до начала реализации. Небольшие исправления, например опечатки или мелкие правки
документации, можно сразу отправлять в PR.

### 2. Форк и ветка

1. Сделайте форк репозитория в свой аккаунт GitHub (участники с правом записи
   могут создавать ветки в этом репозитории).
2. Создайте ветку от `main` с понятным названием, например `42-fix-page-rename`
   для issue #42. Обязательного формата имени нет.

### 3. Разберитесь в кодовой базе

Перед тем как что-то менять, прочитайте [`architecture.md`](architecture.md) (на английском) —
обзорную карту кода. Найти относящиеся к задаче требования и архитектурные решения
поможет [docs/README.md](README.md) (на английском).

### 4. Внесите изменение

- Обоснование каждого крупного решения описано в
  [decisions/](decisions/) (ADR неизменяемы: чтобы изменить решение,
  пишут новый ADR, а не правят старый).
- Для нового или изменённого поведения добавляйте подходящие тесты. Модульные и
  виджет-тесты повторяют структуру `lib/` в `test/lib/`; интеграционные сценарии
  находятся в `integration_test/`.
- Никогда не правьте сгенерированные файлы (`*.g.dart`, `*.freezed.dart`) —
  вместо этого перегенерируйте их командой `dart run build_runner build`.
- Никаких `print()` в продакшен-коде — используйте `package:logging`.
- При изменении поведения, форматов или архитектурных решений обновляйте затронутую документацию.

### 5. Проверьте изменение

Для изменений кода:

- При необходимости перегенерируйте код, затем выполните `dart run scripts/lint.dart` и `flutter test`.
- Если изменение затрагивает пользовательские сценарии, запустите соответствующие интеграционные тесты.
- Опишите в PR ручные проверки и то, что не удалось проверить.

Если меняется только документация, проверки кода, тесты и кодогенерация не нужны.
Вместо этого:

- Проверьте точность текста, ссылки, пути и примеры команд. Не запускайте
  разрушительные или изменяющие состояние команды только ради проверки примера.
- Проверьте отображение Markdown, особенно таблиц и блоков кода.
- Обновите существующие переводы.
- Выполните `git diff --check` и опишите проверки в PR.

### 6. Откройте PR

Отправьте ветку и откройте пул-реквест в `main`, заполнив шаблон PR (что
изменилось, зачем и как это проверялось). Добавьте ссылку на связанное issue,
если оно есть; используйте `Closes #42`, если PR решает эту задачу.

### 7. Ревью и слияние

- Владелец репозитория рассматривает PR и принимает окончательное решение о принятии изменений.
- Исправления по замечаниям отправляйте в ту же ветку — новый PR открывать не нужно.
- Слияние PR в `main` выполняет владелец репозитория.

## Релизы

Для изменений, заметных пользователю, обновляйте `CHANGELOG.md` в том же PR.
Процесс выпуска описан в [release-process.md](release-process.md) (на английском).

## Переводы

Переводы размещаются рядом с исходным документом; к имени файла добавляется
суффикс языка, например `README_RU.md`.

- При изменении документа обновляйте существующие переводы в том же PR.
- В начале документа размещайте ссылки на доступные языковые версии,
  выделяя текущий язык полужирным.
- В переводах ссылайтесь на документы на том же языке, если перевод доступен;
  иначе — на исходный документ.

## Настройка окружения

Установите Flutter SDK с версией Dart, соответствующей ограничению
`environment.sdk` в [pubspec.yaml](../pubspec.yaml).

```bash
git clone https://github.com/LonelyGriffin/noetec.git   # или ваш форк
cd noetec
flutter pub get
dart run build_runner build
dart run scripts/setup_project.dart   # устанавливает git-хук pre-commit
```

Хук pre-commit автоматически выполняет проверки проекта перед коммитом.

### Повседневные команды

Все команды запускаются из корня репозитория.

| Команда | Назначение |
|---|---|
| `dart run scripts/format.dart` | Применение принятого в проекте форматирования кода |
| `dart run scripts/lint.dart` | Запуск проверок качества кода |
| `flutter test` | Запуск модульных и виджет-тестов (`test/`) |
| `dart run scripts/run_integration_tests.dart` | Запуск интеграционных тестов (`integration_test/`) |
| `dart run build_runner build` | Кодогенерация (json_serializable и т. п.) — запускайте после изменения сериализуемых классов |
