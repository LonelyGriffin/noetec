# 0007: Модель идентичности нескольких пользователей и реестров синхронизации

[English](0007-user-device-identity-and-registry.md) · [**Русский**](0007-user-device-identity-and-registry_RU.md)

## Контекст (Context)

Файловая синхронизация обменивается состоянием только через каталог `.sync/`; `.noetec/`
хранит локальные, несинхронизируемые метаданные (vault.json, device.json, trusted_keys.json,
WAL, конфликты). Продукту нужна настоящая поддержка нескольких пользователей: несколько пользователей на
хранилище, у каждого несколько устройств, с атрибуцией («какой пользователь сделал эту
запись») и авторизацией («вносят вклад только авторизованные пользователи/устройства»).

Модель «пользователь = устройство-владелец» была отклонена: пользователь должен существовать независимо от любого
отдельного устройства и быть восстановимым. Серверная идентичность (passkey/OIDC) и
реестры по принципу «сначала данные» были отклонены для файловой фазы (см. «Рассмотренные альтернативы»).
Выбранная модель — иерархическая криптографическая идентичность с восстановлением по seed.

## Решение (Decision)

### 1. Идентичность (два уровня)

- **Пользователь** — это пара ключей идентичности Ed25519, детерминированно выведенная из
  32-байтового seed (резервная копия — мнемоника BIP39).
- **Устройство** — независимая пара ключей Ed25519, одна на машину, НЕ выведенная
  из seed, — поэтому устройство можно отозвать, не затрагивая идентичность.
- Устройство привязано к своему пользователю **сертификатом**:
  `{deviceUuid, devicePublicKey, userId, deviceName, issuedAt}`, подписанным
  ключом идентичности пользователя.
- Ключ идентичности выводится из seed через **HKDF-SHA256** (RFC 5869):
  `salt = "noetec.identity.v1"`, `info = "noetec-identity-key"`, 32-байтовый выход
  используется как секретный seed Ed25519. Мнемоника — лишь человекочитаемая резервная копия
  seed (восстанавливается через `mnemonicToEntropy`); PBKDF2 не используется.

Цепочка атрибуции: `entry → device (device key) → user (certificate) →
authorized (registry)`.

### 2. Секреты

Seed, приватный ключ идентичности и приватный ключ устройства живут в
`flutter_secure_storage`; они **MUST NOT** (не должны) записываться в хранилище или в зону
синхронизации. Seed показывается один раз при создании идентичности — для резервной копии.

### 3. Реестры

- `.sync/users.json` — один реестр пользователей, подписанный владельцем. Каждая запись:
  `{userId, name, publicKey, role, addedBy, updatedAt, removedAt, signature}`.
  Файл несёт `{version, revision, parent, owner_user_id, users,
  signature}` (подпись всего файла ключом идентичности владельца; каждая запись
  подписана `addedBy`).
- `.sync/devices/<userId>.json` — один файл на пользователя, подписанный ключом идентичности этого
  пользователя (весь файл + каждая запись). Уникальное имя файла делает его
  бесконфликтным по построению (тот же принцип, что и в OpLog): каждый пользователь управляет
  только своим файлом, поэтому два пользователя, добавляющие устройства, никогда не конфликтуют.

### 4. Роли

`role: owner | member` в записях пользователей. Для v1 применяется только `owner` (владелец
администрирует `users.json`). Детализированные роли отложены до серверной синхронизации —
их нельзя обеспечить при файловой синхронизации.

### 5. Слияние реестра (users.json)

Метки версий — ключи HLC (`<physicalMs>-<counter>-<deviceId>`, покомпонентное
упорядочивание — см. `lib/entity/hlc.dart`). Разрешение конфликтов — **LWW по записям**,
а не по файлам: для каждой записи сравниваются `updatedAt` / `removedAt` (tombstone) по
HLC; одинаковые HLC разрешаются детерминированно по каноническому JSON. Трёхстороннее
слияние использует `parent` как общего предка. LWW на уровне файла (больший `revision`)
применяется только как запасной вариант, когда общего предка нет, и всегда сообщает о результате,
а не отбрасывает молча.

## Статус (Status)

Принято (Accepted).

Пересмотрено 2026-09-08: пункт о PBKDF2 в §1 отозван (он противоречил первому
пункту и положению о HKDF). Ключ идентичности выводится из 32-байтового энтропийного
seed через HKDF-SHA256; мнемоника — только резервная копия. PBKDF2 не является частью
вывода ключа.

Заменяет ADR-0003 (идентичность устройства отложена): идентичность устройства теперь
реализована (`lib/entity/device/device_identity.dart`,
`lib/service/device_service.dart`). Поле frontmatter `modified_by` остаётся
отложенным и необязательным — атрибуция живёт в OpLog (deviceId + подпись).

## Последствия (Consequences)

- Положительно: настоящая многопользовательская работа с управлением устройствами по пользователям; полная атрибуция
  `entry → device → user`; идентичность восстанавливаема из seed; отзыв устройства
  независим от идентичности; реестры сходятся детерминированно при
  одновременных правках.
- Положительно: `devices/<userId>.json` убирает класс конфликтов «одновременные devices.json»
  и позволяет каждому файлу реестра нести подпись всего файла.
- Отрицательно: две пары ключей и два вида реестров (больше понятий и кода).
- Отрицательно: ключ идентичности (или seed) присутствует на каждом устройстве пользователя,
  поэтому компрометация одного устройства компрометирует идентичность.
- Отрицательно (унаследованное ограничение файлового подхода, без изменений с sync-security.md): нет
  предотвращения записи на физическом уровне (отказ происходит во время чтения).

## Рассмотренные альтернативы (Alternatives considered)

- **Пользователь = устройство-владелец** — отклонено: нет независимого пользователя, нет восстановления.
- **Плоская модель (пользователь = именованная группа устройств)** — отклонено: у пользователя нет
  криптографической идентичности; потеря всех устройств означает потерю пользователя.
- **Реестр по принципу «сначала данные» (пользователи как документы, синхронизируемые через OpLog)** — отклонено:
  цикл начальной загрузки и более сложный анализ безопасности.
- **Внешняя идентичность (passkey/OIDC)** — отложено до серверной версии: добавляет
  доверенную третью сторону и онлайн-зависимость, что конфликтует с local-first.
- **Единый `devices.json`** — отклонено: одновременные правки разных пользователей
  требуют слияния без подписанта всего файла; файлы по пользователям избегают этого класса
  конфликтов и остаются полностью подписанными.
- **LWW по файлам (без слияния)** — отклонено: молча теряет одновременные добавления в
  разные записи.
- **SLIP-0010 (BIP32 для Ed25519) для ключа идентичности** — отклонено: добавляет
  chain code и иерархический вывод, которые этой модели не нужны (ключ
  идентичности — один ключ; ключи устройств независимы), и требует больше
  кода без выгоды.
- **SHA-256(seed) как KDF** — отклонено: нет разделения доменов и это не
  стандарт вывода ключей.
