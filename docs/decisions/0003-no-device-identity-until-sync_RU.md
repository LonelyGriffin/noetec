# 0003: Идентичности устройства нет, пока не реализована синхронизация

[English](0003-no-device-identity-until-sync.md) · [**Русский**](0003-no-device-identity-until-sync_RU.md)

## Контекст (Context)

Целевой дизайн атрибутирует каждое изменение устройству, которое его сделало: идентичность устройства (UUID на устройство, хранимый вместе с другим локальным состоянием устройства) и поле `modified_by: <device-uuid>` в frontmatter каждого файла. Именно атрибуция по устройствам делает осмысленными слияние между устройствами, разрешение конфликтов и журналы операций по устройствам.

Однако синхронизация — единственная функция, которая потребляет атрибуцию по устройствам, — ещё не реализована. Добавить идентичность устройства сейчас означало бы поддерживать жизненный цикл идентичности (генерация, персистентность, именование) и поле frontmatter, которое никто не читает.

## Решение (Decision)

Отложить идентичность устройства. Не генерировать и не хранить UUID устройства и не записывать `modified_by` во frontmatter файлов, пока не реализована синхронизация. Frontmatter в текущем формате не содержит `modified_by`; поле (и идентичность устройства, на которую оно ссылается) будут введены вместе с той работой по синхронизации, которой они нужны.

## Статус (Status)

Принято (Accepted).

## Последствия (Consequences)

- Положительно: меньше кода, который нужно писать, тестировать и поддерживать в фазах до синхронизации, — никакого управления жизненным циклом идентичности без потребителя.
- Положительно: frontmatter остаётся минимальным; записываемые сейчас файлы не засоряются полями-заглушками с бессмысленными значениями.
- Отрицательно: когда появится синхронизация, существующие файлы придётся мигрировать, чтобы добавить `modified_by` (или терпеть его отсутствие), а для существующих хранилищ нужно будет создать идентичность устройства.
- Отрицательно: до тех пор атрибуции изменений нет вообще — это приемлемо только потому, что локально-первичный MVP на одном устройстве имеет ровно одного возможного автора.

## Рассмотренные альтернативы (Alternatives considered)

- **Писать `modified_by` с первого дня с временным ID устройства** — отклонено: добавляет сложность жизненного цикла идентичности до того, как её потребляет хоть одна функция, а семантику временной идентичности, скорее всего, придётся переделывать, когда появится настоящая семантика синхронизации.
- **Сохранить идентичность устройства, но опустить `modified_by`** — отклонено: идентичность, на которую не ссылается ни одно поле, — мёртвый груз; чтобы быть полезными, эти две вещи должны появиться вместе.
