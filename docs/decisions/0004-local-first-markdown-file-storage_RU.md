# 0004: Локально-первичное файловое хранилище как Markdown с YAML-frontmatter

[English](0004-local-first-markdown-file-storage.md) · [**Русский**](0004-local-first-markdown-file-storage_RU.md)

## Контекст (Context)

Noetec нужна модель хранения для заметок, задач и данных совместной работы. Ключевые ценности продукта: полная работоспособность офлайн, владение данными пользователем, человекочитаемое содержимое и совместимость с существующими инструментами (внешние редакторы, контроль версий, сервисы синхронизации файлов). Традиционный подход — собственная база данных приложения или облачный сервис — конфликтует с несколькими из этих ценностей.

## Решение (Decision)

Принять локально-первичное файловое хранилище. Все пользовательские данные хранятся как обычные `.md`-файлы в файловой системе пользователя, каждый начинается с блока YAML-frontmatter, несущего метаданные документа (стабильный `id` документа, `content_hash` для целостности и обнаружения внешних правок, метки времени изменения — при этом `modified_by` отложен согласно ADR-0003). Сами файлы являются источником истины; приложение полностью работоспособно без сетевого соединения, а синхронизация (файловые сервисы вроде Dropbox или Git, серверная или P2P) накладывается сверху асинхронно как более поздняя задача.

## Статус (Status)

Принято (Accepted).

## Последствия (Consequences)

- Положительно: настоящая офлайн-работа — все операции выполняются локально без сетевой зависимости.
- Положительно: данные принадлежат пользователю в открытом, человекочитаемом, совместимом с инструментами формате; файлы можно читать и редактировать вне Noetec и отслеживать в Git.
- Положительно: синхронизация через существующие сервисы синхронизации файлов становится возможной без собственного сервера.
- Отрицательно: приложение должно обнаруживать и терпеть внешние правки своих файлов (отсюда проверка целостности `content_hash`), с чем закрытая база данных никогда бы не столкнулась.
- Отрицательно: запросы, индексация и реляционные операции сложнее над отдельными файлами, чем над базой данных; проверки целостности и согласованности нужно реализовывать явно.
- Отрицательно: обработка конфликтов между устройствами становится проблемой приложения, а не базы данных, — отложена до фаз синхронизации.

## Рассмотренные альтернативы (Alternatives considered)

- **SQLite / встроенная база данных как источник истины** — отклонено: не человекочитаемо, не редактируется напрямую внешними инструментами и запирает данные пользователя в бинарном формате приложения; конфликтует с ценностью файлового владения.
- **Облачное хранилище (удалённый сервер как источник истины, локальный кеш)** — отклонено: нарушает local-first; офлайн становится ухудшенным режимом вместо режима по умолчанию, а владение данными пользователем ослабляется.
- **Обычный markdown без frontmatter** — отклонено: негде хранить стабильный ID документа и хеш целостности, а оба нужны для обнаружения внешних правок и последующей синхронизации.
