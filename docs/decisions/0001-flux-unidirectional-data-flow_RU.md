# 0001: Однонаправленный поток данных во Flux

[English](0001-flux-unidirectional-data-flow.md) · [**Русский**](0001-flux-unidirectional-data-flow_RU.md)

## Контекст (Context)

Noetec нужна архитектура управления состоянием и потоком данных, которая сохраняет растущий набор функций (управление хранилищами, редактирование, персистентность и со временем синхронизацию) предсказуемым и тестируемым. В реактивном UI состояние легко мутируется из многих мест, порождая циклические зависимости, скрытые побочные эффекты и потоки, которые трудно проследить или отладить.

## Решение (Decision)

Принять однонаправленный поток данных, вдохновлённый Flux. Цикл таков:

1. В View происходит действие пользователя.
2. View вызывает `command.run(param)` у команды системы.
3. Команда выполняет свой обработчик, производя доменные операции над сущностями.
4. Обработчик обновляет реактивное состояние системы (нотифаеры).
5. `WatchingWidget`, наблюдающий за этими нотифаерами, замечает изменение и перестраивается.
6. Цикл повторяется с шага 1.

Свойства этого потока:

- **Однонаправленность** — состояние движется только в одном направлении; циклических зависимостей между системами нет.
- **Явность** — все изменения состояния идут через команды; ничего не мутирует состояние за кулисами.
- **Изолированность** — система не может напрямую мутировать состояние другой системы.
- **Межсистемное взаимодействие** — если Системе A нужно, чтобы действовала Система B, A вызывает команду B. A может наблюдать за состоянием B, но никогда его не мутирует.

## Статус (Status)

Принято (Accepted).

## Последствия (Consequences)

- Положительно: поток данных явный и легко прослеживается; переходы состояния тестируемы на границе команд; циклические зависимости между системами структурно предотвращены.
- Положительно: представления остаются тонкими (без бизнес-логики, без прямой мутации сущностей), что сохраняет код UI простым.
- Отрицательно: больше шаблонного кода, чем при ad-hoc мутации — каждое изменение состояния требует команды, даже тривиальное.
- Отрицательно: косвенность — читателю нужно пройти цепочку команда → обработчик → нотифаер, чтобы понять, как событие UI приводит к изменению состояния.

## Рассмотренные альтернативы (Alternatives considered)

- **Прямое двустороннее связывание / мутируемое разделяемое состояние** — отклонено: ведёт к скрытым побочным эффектам, циклическим зависимостям и потокам, которые трудно проследить или протестировать.
- **Паттерн Bloc / event-sink** — отклонено: даёт похожие гарантии однонаправленности, но с более тяжёлой церемонией (события + состояния + блоки), чем выбранная здесь модель команд и нотифаеров; выбранный стек достигает того же однонаправленного потока с меньшей косвенностью (см. ADR-0005).
- **Единое глобальное хранилище в стиле Redux** — отклонено: единое неизменяемое глобальное дерево состояния плюс редьюсеры добавляют нагрузку по нормализации и косвенность, которые не нужны, когда каждая функциональная система владеет своим реактивным состоянием.
