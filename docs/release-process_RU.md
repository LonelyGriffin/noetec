# Процесс релиза

[English](release-process.md) · [**Русский**](release-process_RU.md)

Как Noetec версионирует и помечает тегами релизы. Changelog живёт в
[CHANGELOG_RU.md](../CHANGELOG_RU.md) (формат Keep a Changelog); этот файл описывает
механику выпуска релиза из него.

## Когда выпускать релиз

- Noetec в **pre-alpha**: релизы — частые, малоторжественные контрольные точки
  рабочего состояния, а не отполированные поставки продукта. Выпускайте релиз, когда `main`
  в состоянии, которое стоит зафиксировать — как правило, после завершения вехи (возможности
  редактора, движок синхронизации, поддержка платформы, …).
- В pre-alpha **никогда не пропускайте** версию только потому, что «ничего большого не изменилось»;
  changelog — это сигнал прогресса проекта.
- Никакого релиза из красного или непроверенного состояния: ветка должна проходить
  `flutter analyze` и `flutter test` до того, как её пометят тегом.

## Версионирование

Семантическое версионирование, `MAJOR.MINOR.PATCH`, из `version:` в `pubspec.yaml`:

| Повышение | Когда |
|---|---|
| MAJOR | Ломающие изменения пользовательского поведения или форматов данных/файлов (дисциплина после 1.0; в pre-alpha изменения формата файлов нормальны и отмечаются в changelog) |
| MINOR | Новые возможности, новые функции |
| PATCH | Исправления ошибок, небольшие улучшения, документация |

Версии pre-alpha — `0.x.y`, всё может измениться в любой момент.

## Шаги

Релиз — это небольшой PR в релизной ветке плюс тег и GitHub Release.

1. **Подготовьте ветку.** От вершины `main` создайте релизную ветку:
   `release/vX.Y.Z`.
2. **Заполните changelog.** В `CHANGELOG.md` перенесите записи из `[Unreleased]`
   под новый заголовок версии `## [X.Y.Z] - YYYY-MM-DD` (дата тега в ISO 8601,
   а не дата последнего коммита), затем добавьте сверху свежий пустой
   раздел `## [Unreleased]`.
3. **Повысьте версию.** Установите `version: X.Y.Z` в `pubspec.yaml`.
4. **Проверьте.** Прогоните полный набор: `flutter analyze` и `flutter test` должны
   быть зелёными.
5. **PR и слияние.** Откройте PR (`release/vX.Y.Z` → `main`) с
   changelog и повышением версии в качестве полезной нагрузки. Релизный PR ревьюится и
   вливается как любой другой — вливает только сопровождающий, на GitHub.
6. **Тег.** После слияния пометьте тегом коммит слияния в `main`:
   `git tag vX.Y.Z -m "Release vX.Y.Z" && git push origin vX.Y.Z`.
   Формат тега — строчный префикс `v` + точная версия из `pubspec.yaml`
   (`v0.2.0`), никогда не голое `0.2.0`.
7. **GitHub Release.** Создайте релиз для тега
   (`gh release create vX.Y.Z --title "vX.Y.Z" --notes-file <notes>`):
   примечания к релизу — это раздел changelog для этой версии дословно
   (записи + заголовки, без строки заголовка версии). Пометьте его pre-release,
   пока проект в pre-alpha.
8. **Замкните цикл.** Убедитесь, что версия в `pubspec.yaml`, git-тег и
   заголовок changelog несут одинаковый `X.Y.Z`.

## Практические правила

- Changelog — источник истины для *что изменилось*; тег — источник истины для
  *какой коммит является релизом*. Если они расходятся, побеждает changelog, а тег и примечания исправляются.
- Никогда не редактируйте раздел выпущенной версии; исправления идут в новую версию
  (при необходимости — `patch`-релизом).
- Раздел `[Unreleased]` — это место, куда попадают все новые PR: когда ваша работа
  добавляет, меняет или исправляет что-то видимое пользователю, добавьте строку в
  `CHANGELOG.md` в том же PR. Тогда сам релиз становится в основном механическим.
- Агенты никогда не пушат теги в защищённую историю `main` и никогда не вливают; пуш тега
  и создание релиза — действия сопровождающего (или явно
  делегированное действие агента со свежим токеном GitHub, согласно
  процессу git/GitHub проекта).
