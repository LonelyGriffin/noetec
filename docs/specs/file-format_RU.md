# Формат файла страницы Noetec

[English](file-format.md) · [**Русский**](file-format_RU.md)

**Версия формата: 1**

Этот документ — нормативная спецификация формата файла страницы Noetec на диске.
Это контракт: реализации (парсеры, сериализаторы, движки синхронизации,
внешние инструменты) **MUST** (обязаны) соответствовать этому документу. Если
реализация расходится с этой спецификацией, это баг в
реализации, а не в этом документе.

Ключевые слова **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** и **MAY**
в этом документе интерпретируются так, как описано в RFC 2119.

Эта спецификация самодостаточна: читатель может реализовать корректный парсер
и сериализатор для формата файла страницы только по этому документу.

---

## 1. Обзор

Страница Noetec хранится как один текстовый файл в кодировке UTF-8 с расширением `.md`.
Файл состоит из двух частей, по порядку:

1. Необязательный **блок frontmatter**, несущий метаданные страницы.
2. **Тело содержимого**: GitHub-Flavored Markdown, в котором каждый блок верхнего
   уровня обёрнут в **блочную директиву в ограждении**, несущую стабильный
   идентификатор блока.

```text
┌─────────────────────────────┐
│ ---                         │ ┐
│ id: <uuid>                  │ │
│ content_hash: sha256:<hex>  │ │  блок frontmatter (при чтении —
│ modified: <iso8601>         │ │  необязателен, при записи обязателен)
│ ---                         │ ┘
│                             │
│ ::: {#block-id-1}           │ ┐
│ First block markdown.       │ │
│ :::                         │ │  тело содержимого
│                             │ │
│ ::: {#block-id-2}           │ │
│ Second block markdown.      │ │
│ :::                         │ ┘
└─────────────────────────────┘
```

---

## 2. Кодировка символов и переводы строк

- Файл **MUST** (обязан) быть в кодировке UTF-8 без метки порядка байтов (BOM). Парсер
  **MAY** (может) принимать и молча отбрасывать ведущий BOM.
- При **записи** все переводы строк в файле **MUST** (обязаны) быть LF (`\n`, U+000A).
- При **чтении** парсер **MUST** (обязан) нормализовать переводы строк CRLF (`\r\n`) и одиночный CR (`\r`)
  в LF до любой дальнейшей обработки (обнаружение frontmatter,
  хеширование, разбор блоков). Поэтому файлы, созданные в Windows, — валидный
  вход; их нормализация часть разбора, а не ошибка.

Нормализованная форма (только LF) — каноническая. Везде, где эта
спецификация говорит «содержимое» (включая вход хеша в §5), имеется в виду
**нормализованное** содержимое.

## 3. Блок frontmatter

### 3.1 Разделители и размещение

Блок frontmatter, когда он присутствует:

- **MUST** (обязан) начинаться со смещения 0 файла (после отброшенного BOM).
- **MUST** (обязан) начинаться со строки, состоящей ровно из трёх символов
  дефиса-минуса `---`.
- **MUST** (обязан) заканчиваться последующей строкой, состоящей ровно из `---`.
- Текст между этими двумя строками-разделителями — **тело frontmatter**, и
  он **MUST** (обязан) быть единственным YAML-отображением (пары `key: value`, по одной на строку).

Всё после закрывающей строки-разделителя — тело содержимого. Если строка
непосредственно после закрывающего разделителя пуста, парсер **MUST** (обязан)
поглотить эту единственную пустую строку как разделитель (то есть она не является частью
тела содержимого).

### 3.2 Схема

Отображение frontmatter определяет следующие ключи:

| Ключ           | Тип    | Обязателен при записи | Описание                                                                    |
| -------------- | ------ | --------------------- | --------------------------------------------------------------------------- |
| `id`           | string | **MUST**              | Стабильный идентификатор страницы. UUID (RFC 4122, рекомендуется версия 4), нижний hex с дефисами. Стабилен при переименованиях и переносах файла. |
| `content_hash` | string | **MUST**              | `sha256:` и следом 64-символьный hex-дайджест SHA-256 тела содержимого в нижнем регистре, вычисленный по §5. Используется для обнаружения внешних правок. |
| `modified`     | string | **MUST**              | Метка времени последнего сохранения в виде даты-времени ISO 8601 в UTC, например `2026-01-15T10:30:00.000Z`. **MUST** (обязана) разбираться парсерами ISO 8601. |
| `modified_by`  | string | **SHOULD**            | UUID устройства, выполнившего последнее сохранение. Опускается, когда неизвестен. |

В отображении **MAY** (могут) появляться дополнительные ключи. Парсер **MUST** (обязан) игнорировать незнакомые
ключи и **MUST NOT** (не должен) падать из-за них.

Порядок ключей в отображении при чтении не важен. При записи реализации
**SHOULD** (следует) выводить ключи в порядке, показанном выше, для детерминированных диффов.

### 3.3 Форма сериализации

При записи блок frontmatter **MUST** (обязан) быть сериализован ровно так:

```text
---\n
id: <uuid>\n
content_hash: sha256:<hex>\n
modified: <iso8601>\n
[modified_by: <device-uuid>\n]
---\n
\n
<content body>
```

То есть: открывающий разделитель, по одной строке `key: value` на ключ (один пробел после
двоеточия, значения без кавычек, если YAML не требует кавычек), закрывающий разделитель,
одна пустая строка-разделитель, затем тело содержимого.

### 3.4 Отсутствующий, некорректный и граничный вход (нормативно)

Парсер **MUST** (обязан) обрабатывать следующие входы без ошибки:

1. **Отсутствующий frontmatter.** Если файл не начинается со строки-разделителя `---`,
   парсер **MUST** (обязан) трактовать весь файл как тело содержимого и
   **MUST** (обязан) синтезировать свежий frontmatter: новый случайный UUID для `id`,
   `content_hash` по §5, `modified` — текущее время UTC.
2. **Некорректный YAML.** Если блок, похожий на frontmatter, присутствует (файл начинается
   с `---`), но его тело не разбирается как YAML или разбирается во что-то
   иное, чем YAML-отображение, парсер **MUST** (обязан) отбросить frontmatter и
   вести себя как в случае 1: **весь файл, включая некорректный блок**, трактуется
   как содержимое, а свежий frontmatter со свежим `id` синтезируется.
   Парсер **MUST NOT** (не должен) падать или отвергать файл.
3. **Отсутствующие ключи.** Если YAML-отображение разбирается, но отдельные ключи
   отсутствуют: `id` **MUST** (обязан) быть перегенерирован как свежий UUID; `modified` **MUST**
   (обязана) по умолчанию принять текущее время UTC; `content_hash` **MUST** (обязан) быть пересчитан по
   §5; `modified_by` считается отсутствующим.
4. **Пустой файл.** Файл нулевого размера или файл, содержащий только пробелы,
   **MUST** (обязан) разбираться в пустое тело содержимого плюс свежий frontmatter (свежий
   `id`, текущий `modified`).
5. **Переводы строк Windows.** Файл с переводами строк CRLF (или одиночным CR) —
   валидный вход, и он **MUST** (обязан) обрабатываться по §2 (сначала нормализация, затем случаи
   1–4 применяются к нормализованному тексту).
6. **Незавершённый frontmatter.** Если файл начинается с `---`, но закрывающей
   строки `---` нет, вход считается некорректным (случай 2): весь
   файл — содержимое, синтезируется свежий frontmatter.

В случаях 1, 2, 4 и 6 идентичность страницы создаётся заново при каждом свежем
разборе этого файла, пока страница не сохранена; при сохранении синтезированный
frontmatter записывается на диск, и `id` с этого момента становится стабильным.

## 4. Блочные директивы

### 4.1 Назначение

Тело содержимого — это GitHub-Flavored Markdown. Каждый блок верхнего уровня
документа **MUST** (обязан) быть обёрнут в **блочную директиву в ограждении**, которая связывает
markdown блока со стабильным уникальным **идентификатором блока**. Идентификаторы блоков — якорь
для редактирования, журнала операций и синхронизации: они позволяют системе адресовать блок
независимо от его позиции в файле.

### 4.2 Синтаксис

Блочная директива состоит из **открывающего ограждения**, нуля или более строк
содержимого блока и **закрывающего ограждения**:

```text
::: {#<block-id>}
<block markdown, zero or more lines>
:::
```

- **Открывающее ограждение.** Строка, соответствующая: три или более символов `:`, необязательные
  пробелы, блок атрибутов `{...}`, необязательные замыкающие пробелы, конец
  строки. Формально: `^:{3,}\s*\{([^}]*)\}\s*$`.
- **Закрывающее ограждение.** Строка, соответствующая: три или более символов `:`, необязательные
  замыкающие пробелы, конец строки. Формально: `^:{3,}\s*$`.
- **Блок атрибутов.** Текст между `{` и `}` открывающего ограждения, в
  синтаксисе атрибутов в стиле pandoc. Определены следующие атрибуты:
  - `#<id>` — идентификатор блока. **MUST** (обязан) присутствовать при записи. Идентификатор —
    непустая строка из словесных символов и дефисов (`[\w-]+`, то есть
    `A–Z a–z 0–9 _ -`). Он **MUST** (обязан) быть уникальным внутри файла.
  - `.<class>` — аннотация класса. Сейчас зарезервирована; парсеры **MUST**
    (обязаны) принимать и игнорировать её.
  - `key="value"` / `key='value'` / `key=value` — произвольные метаданные
    ключ-значение. Парсеры **MUST** (обязаны) принимать незнакомые ключи и **MUST** (обязаны) сохранять их
    при round-trip, когда это осуществимо.

При записи реализации **MUST** (обязаны) выводить ровно три двоеточия и один
пробел перед блоком атрибутов: `::: {#<id>}` и следом любые дополнительные
атрибуты, затем закрывающее ограждение ровно как `:::`.

### 4.3 Содержимое директивы

- Строки между открывающим и закрывающим ограждениями — markdown-содержимое блока.
  Пустой блок (открывающее ограждение сразу за закрывающим
  или только пустые строки между ними) валиден и представляет пустой
  текстовый блок.
- Содержимое блока разбирается как обычный GitHub-Flavored Markdown. Внутри одной
  директивы содержимое **MUST NOT** (не должно) содержать строку, соответствующую шаблону закрывающего
  ограждения `^:{3,}\s*$`; сериализатор **MUST NOT** (не должен) выводить такую строку
  внутри блока, а парсер трактует первую такую строку как закрывающее
  ограждение.
- Директивы **MAY** (могут) быть вложенными (директива может находиться внутри содержимого другой
  директивы). Эта спецификация определяет только плоскую структуру верхнего
  уровня; семантика вложенности определяется моделью блоков и выходит
  за рамки этого документа.
- Блоки верхнего уровня **MUST** (обязаны) отделяться друг от друга ровно одной пустой
  строкой при записи.

### 4.4 «Голый» markdown (нормативно)

Markdown вне любой директивы — например, написанный вручную файл, файл из
внешнего редактора или унаследованное содержимое — валидный вход. Парсер **MUST** (обязан) принимать
его и **MUST** (обязан) обернуть каждый получившийся блок markdown верхнего уровня в свежую
директиву со свежесгенерированным идентификатором блока при следующем сохранении. Поэтому документ,
в котором директив нет вообще, всё равно разбирается: его абзацы становятся блоками.

### 4.5 Встроенное форматирование

Встроенное форматирование внутри содержимого блока использует стандартный Markdown
со следующим отображением на модель блоков:

- `**text**` — полужирный.
- `*text*` — курсив.
- `***text***` — полужирный курсив.
- `[text](url)` — ссылка.

При записи следующие символы в простом тексте **MUST** (обязаны) экранироваться обратным слешем,
когда они встречаются в содержимом буквально:

```text
\  *  _  [  ]  (  )  ~  `  >  #  +  -  =  |  {  }  .  !
```

При чтении обратный слеш перед любым из этих символов **MUST** (обязан)
интерпретироваться как сам символ (стандартное жёсткое экранирование CommonMark).

## 5. Алгоритм хеша содержимого

`content_hash` обнаруживает внешнее изменение: изменение файла вне
собственного пути сохранения приложения даёт другой хеш.

Хеш **MUST** (обязан) вычисляться следующим образом, ровно в этом порядке:

1. Прочитать файл как текст UTF-8.
2. **Нормализовать переводы строк** в LF по §2.
3. **Убрать блок frontmatter**: открывающую строку `---`, тело YAML,
   закрывающую строку `---` и единственную пустую строку-разделитель непосредственно
   после неё (если она есть). Остаётся тело содержимого. (Если frontmatter
   отсутствует или некорректен, всё нормализованное содержимое файла — это
   тело содержимого, по §3.4.)
4. Закодировать тело содержимого в байты UTF-8.
5. Вычислить дайджест SHA-256 этих байтов.
6. Отформатировать как `sha256:` и следом 64-символьный hex-дайджест в нижнем регистре.

Хранимое во frontmatter значение `content_hash` **MUST** (обязано) быть равно результату
этого алгоритма, применённого к телу содержимого самого файла на момент последнего
сохранения. Потребитель, который пересчитывает хеш файла на диске и обнаруживает
несовпадение, **MUST** (обязан) трактовать файл как изменённый извне.

Заметим, что вход хеша — только тело содержимого, никогда frontmatter,
поэтому обновление `modified` или `modified_by` при сохранении само по себе не меняет
хеш.

## 6. Требования к round-trip

Реализация, которая разбирает и заново сериализует соответствующий спецификации файл, **MUST**
(обязана) удовлетворять:

- **Стабильность идентификаторов**: `id` страницы и все идентификаторы блоков, присутствовавшие на входе,
  на выходе сохраняются без изменений.
- **Стабильность содержимого**: повторный разбор сериализованного выхода даёт последовательность блоков,
  равную входной (те же идентификаторы, тот же текст, то же форматирование,
  те же ссылки).
- **Согласованность хеша**: после любого сохранения, в котором содержимое менялось,
  записанный `content_hash` совпадает с алгоритмом из §5, применённым к записанному
  файлу.

Точный побайтовый round-trip произвольных отступов, отредактированных вручную, не
требуется; требуется семантический round-trip модели блоков.

## 7. Пример

Полный файл страницы, соответствующий спецификации:

```markdown
---
id: 3f8a2c1e-9b7d-4e5f-a6c8-1d2e3f4a5b6c
content_hash: sha256:9b74c9897bac770ffc029102a200c5de
modified: 2026-08-26T17:45:12.310Z
modified_by: 7c1e2d3a-4b5f-4a6b-8c9d-0e1f2a3b4c5d
---

::: {#b-welcome}
Welcome to **Noetec**.
:::

::: {#b-todo}
- [ ] Read the [file format spec](https://example.com/spec)
:::
```

## 8. Версионирование

- Этот документ определяет **версию формата 1**. В самом файле для версии 1 нет
  маркера версии; описанный здесь формат — неявная
  базовая линия.
- Любое будущее изменение правил этого документа (схема frontmatter, синтаксис
  ограждений, алгоритм хеша, правила нормализации) **MUST** (обязано) публиковаться как новая
  нумерованная версия этой спецификации и **MUST** (обязано) вводить явный
  индикатор версии в файле, если изменение не читается обратно парсерами версии
  1.
- Каждая версия спецификации **MUST** (обязана) поставляться как минимум с одним новым **эталонным примером (golden fixture)**:
  файлом-примером, закоммиченным в репозиторий, плюс ожидаемый результат разбора, используемый
  тестами round-trip для фиксации контракта. Эталонные примеры старых версий
  **MUST** (обязаны) сохраняться и **MUST** (обязаны) продолжать проходить: новые парсеры остаются способными
  читать старые файлы, либо в новой версии указан явный путь миграции.
- Изменения формата и изменения этой спецификации **MUST** (обязаны) попадать в репозиторий
  вместе: изменение реализации без соответствующего повышения версии спецификации
  и эталонного примера неполно.
