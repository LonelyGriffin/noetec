# Noetec

[English](CLAUDE.md) · [**Русский**](CLAUDE_RU.md)

Точка входа для ИИ-агентов, пишущих код. Держите этот файл компактным: он автоматически подставляется в
каждую сессию, поэтому содержит только всегда верные правила и указатели. Детали живут в
документации и навыках, ссылки на которые ниже — открывайте их только когда задача затрагивает их область.

## Языковые правила (Language rules)

- **Ответы в чате: русский.**
- **Комментарии в коде и документация: английский.**
- **Планы реализации: русский.**

## Жёсткие правила (Hard rules)

- **Никогда не запускайте приложение сами** (`flutter run`, скрипты запуска, симуляторы).
  Пользователь запускает его вручную, чтобы проверить, что оно стартует.
- Никогда не редактируйте сгенерированные файлы (`*.g.dart`, `*.freezed.dart`) — перегенерируйте их через
  build_runner.
- Никаких `print()` в продакшен-коде — используйте `package:logging`.
- Никаких `setState()` во вью-моделях — используйте реактивную экосистему `it`
  (watch_it / listen_it / command_it).
- **Только Павел одобряет и вливает.** Агенты НИКОГДА не пушат в `main`, НИКОГДА не вливают,
  НИКОГДА не одобряют, НИКОГДА не делают `git checkout main`. Защита ветки `main` это обеспечивает.
- **Работайте в изолированном worktree, никогда в общем клоне.** Все агенты используют одну
  машину, поэтому общий `git checkout` переключает ветку под остальными и оставляет
  их незакоммиченную работу. Начинайте каждую задачу с
  `multica repo checkout https://github.com/LonelyGriffin/noetec.git` (изолированный
  присоединённый worktree), затем создавайте ветку `NOET-XX` внутри него — см. навык
  `git-github-workflow`. Никогда не делайте `git checkout`/`reset`/`rebase` в
  общем каталоге.

## Команды

Все команды выполняются из корня репозитория.

| Команда | Назначение |
|---|---|
| `dart run scripts/lint.dart` | Полный линт: проверка формата + `dart analyze` + заголовки копирайта (изменённые файлы) |
| `dart run scripts/format.dart` | Форматирование проекта (ширина строки 180 + висячие запятые, из `formatter:` в `analysis_options.yaml`) |
| `dart analyze` | Статический анализ (`analysis_options.yaml`, flutter_lints + дополнительные правила) |
| `dart run scripts/setup_project.dart` | Установить git-хук pre-commit (формат + анализ + копирайт на проиндексированных файлах) |
| `flutter test` | Запустить набор модульных и виджет-тестов (`test/`) |
| `dart run scripts/run_integration_tests.dart` | Запустить интеграционные тесты (`integration_test/`) — `--slow` / `--speed N` / `--hud-corner` включают HUD, за которым можно наблюдать глазами; см. навык `integration-testing` |
| `dart run build_runner build` | Генерация кода (json_serializable и т. п.) |
| `dart run build_runner watch` | Генерация кода в режиме наблюдения |

## Соглашения

- DI: `get_it`, все регистрации в `lib/app/configure_di.dart`.
- Сервисы: `abstract interface class IXxxService` + `XxxServiceImpl` в одном файле.
- Тесты повторяют `lib/` под `test/lib/` (модульные и виджет-тесты — Developer, который прогоняет
  полный набор `flutter test` перед передачей); интеграционные сценарии живут в
  `integration_test/` (QA, для пользовательского поведения) — QA коммитит и пушит свои
  изменения `integration_test/` в ветку, которую проверяет. Никаких тестов на тривиальную
  логику; никакого дублирующего покрытия.
- Документация — это контракт: спецификации в `docs/specs/` нормативны (RFC 2119),
  решения в `docs/decisions/` — неизменяемые ADR (заменяйте новым
  ADR, никогда не правьте).
